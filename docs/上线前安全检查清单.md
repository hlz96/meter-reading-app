# 上线前安全检查清单

> 基于当前代码逐项核实(非通用模板)。每项标注:证据位置、风险、改法、验证方式。
> 优先级:🔴 必须改(不改会出事) / 🟡 强烈建议 / 🟢 确认即可(已做对)

## 🔴 P0 — 上线前必须处理

### 1. JWT_SECRET 必须用环境变量覆盖默认值
- **证据**:`backend/src/main/resources/application.yml:39`
  默认 `JWT_SECRET: dev-only-secret-please-override-in-prod-at-least-32-bytes`
- **风险**:此默认值在代码库里公开。若生产忘记设 `JWT_SECRET`,攻击者可用它**自己签发合法 access token**,伪造任意 userId/orgId/role,完全绕过鉴权。这是本项目最高危的点。
- **改法**:部署时必须注入环境变量。
  ```bash
  export JWT_SECRET=$(openssl rand -base64 48)
  ```
  `deploy/.env` 里 `JWT_SECRET=改成至少32位的随机字符串` 必须替换为真实随机串。
- **验证**:启动后端后,用旧默认密钥手工签一个 token 调 `/api/v1/auth/me`,应返回 401。

### 2. 关闭短信验证码明文回传
- **证据**:`backend/.../auth/AuthController.java:37`
  ```java
  return ApiResponse.ok(new SmsCodeResponse(code, smsProperties.ttlSeconds()));
  ```
  注释自述:"骨架阶段响应回传验证码,便于联调/测试"。
- **风险**:任何人调 `POST /api/v1/auth/sms-code` 就能直接拿到验证码,短信验证形同虚设——可用于任意手机号注册、撞库、刷注册。
- **改法**:生产环境不要把 `code` 放进响应。改为只返回 `expiresInSeconds`,`code` 仅通过真实短信通道下发。建议用 profile 区分:dev 回传、prod 不回传。
- **验证**:prod 环境调 sms-code,响应体不含 `code` 字段。

### 3. 生产密码/密钥不得使用示例值
- **证据**:`deploy/.env.example` 中 MySQL/Redis 密码均为占位("改成一个强xx密码")。
- **风险**:若直接 `cp .env.example .env` 未改,数据库/Redis 用弱口令。虽然 compose 已限制只监听 `127.0.0.1`(见下 P2-9),但纵深防御仍要求强口令。
- **改法**:`.env` 每个密码用强随机串;确认 `.env` 在 `.gitignore` 中(已确认 `deploy/.gitignore` 忽略)。
- **验证**:`git status` 确认 `.env` 未被跟踪;`grep 改成 deploy/.env` 无输出。

## 🟡 P1 — 强烈建议上线前确认

### 4. CORS 策略未显式配置
- **证据**:全后端无 `cors` / `@CrossOrigin` / `addMapping` 配置(已全局 grep 确认)。
- **现状分析**:本项目采用**同源部署**(前端静态资源与 API 同域,由 nginx 反代 `/api`),因此正常情况下不需要 CORS——这是合理的架构选择,不是漏洞。
- **要确认的**:上线后前端确实与后端同源。若未来出现独立域名的前端(如 App 套壳、第三方接入),需显式配置白名单 CORS,**不要**图省事开 `allowedOrigins("*")` + 允许凭证。
- **验证**:从非同源页面 fetch API,浏览器应因无 CORS 头而拦截(同源部署下预期如此)。

### 5. 确认所有写操作都有角色注解(已逐个核对 ✅,列此备查)
已核对全部 Controller 的 `@PreAuthorize` 覆盖:

| 接口 | 注解 | 是否合理 |
|---|---|---|
| 台账 增/改/删(company/meter) | `hasRole('ADMIN')` | ✅ |
| 周期 增/改/结算 | `hasRole('ADMIN')` | ✅ |
| 读数 提交/批量/修正 | `hasAnyRole('ADMIN','READER')` | ✅ |
| 读数 审核/批量审核 | `hasRole('ADMIN')` | ✅ |
| 报表/催缴/导出 | `hasAnyRole('ADMIN','VIEWER'[,'READER'])` | ✅ |
| 成员 列表/改角色/邀请 | `hasRole('ADMIN')` | ✅ |
| 导入模板/导入 | ADMIN / ADMIN+READER | ✅ |

- **注意点**:GET 类查询(`/companies`、`/meters`、`/periods`、`/readings` 的 list)**故意不加角色注解**,因为已登录用户都可读、且靠 orgId + READER 公司范围做数据隔离(见下第 6 项)。这是设计选择,合理。

### 6. 租户数据隔离(orgId)—— 已做对 ✅,列此备查
- **证据**:`ReadingService` 每个查询都强制 `orgId` 过滤;`update`/`audit` 走 `findByIdAndOrgId`(他组织 id 直接 NOT_FOUND);`auditBatch` 用 `findByOrgIdAndIdIn`(他组织 id 静默忽略);`submit` 校验 meter/period 都 `findByIdAndOrgId`。
- **结论**:多租户越权防护到位。这是比角色控制更容易出事的维度,此项目处理得成熟。
- **建议的回归测试**:构造两个组织 A/B,以 A 身份尝试 `GET /readings?periodId=<B的周期>`、`PUT /readings/<B的记录id>`,都应查不到/改不到。

### 7. `/members/join` 无角色注解 —— 确认是否符合预期
- **证据**:`MemberController.java:64` 的 `join` 无 `@PreAuthorize`,仅需登录。
- **分析**:任何已登录用户凭邀请码加入组织,语义上合理(新人拿邀请码加入)。但要确认:
  - 邀请码有**有效期**和**一次性**校验(`InvitationService.join` 内);
  - 加入后是否有人数/频率限制,避免邀请码泄露后被批量加入。
- **验证**:过期邀请码、已用邀请码调 join 应报错。

## 🟢 P2 — 部署配置核对

### 8. Flyway 生产环境行为
- **证据**:`application.yml:22-24` `baseline-on-migrate: true`,JPA `ddl-auto: validate`。
- **确认**:生产首次启动会自动建表(V1~V3 迁移),JPA 只校验不改表,安全。留意迁移脚本不可在生产回滚。

### 9. MySQL/Redis 不对公网暴露 —— 已做对 ✅
- **证据**:`deploy/docker-compose.yml` 中 mysql/redis 端口均为 `127.0.0.1:xxxx`,backend `127.0.0.1:8080`,仅 nginx 开 80/443。
- **结论**:数据库不触公网,符合安全红线。上线前确认服务器防火墙/安全组也只放行 80/443/22。

### 10. HTTPS
- **证据**:`deploy/README.md` 五节有 certbot 流程,证书放 `nginx/certs/`。
- **确认**:上线务必启用 HTTPS,否则 JWT/密码明文过网。JWT 存在前端 localStorage,HTTP 下极易被中间人窃取。

### 11. 上传文件安全(照片)
- **证据**:`application.yml:37` `upload-dir`,nginx 托管 `/data/uploads`。
- **建议确认**:上传接口是否校验文件类型/大小;nginx 托管 uploads 目录时禁用脚本执行(避免上传恶意文件被当脚本跑)。

## 快速自查命令

```bash
# 1. 确认没有默认 JWT 密钥残留在运行环境
echo $JWT_SECRET | grep -q "dev-only" && echo "❌ 仍是默认密钥!" || echo "✅ 已覆盖"

# 2. 确认 .env 未进 git
cd deploy && git check-ignore .env && echo "✅ .env 已忽略"

# 3. 确认示例占位没被直接用
grep -q "改成" deploy/.env 2>/dev/null && echo "❌ .env 还有占位密码!" || echo "✅ 无占位"
```

## 结论

后端的**鉴权框架和多租户隔离是扎实的**(P1-5、P1-6、P2-9 都已做对),核心风险集中在 **3 个"骨架阶段遗留"配置**:
1. JWT_SECRET 默认值(P0-1)
2. 短信验证码明文回传(P0-2)
3. 示例密码(P0-3)

这三项本质都是"开发便利 vs 生产安全"的开关,上线前逐一关掉即可,不涉及架构改动。
